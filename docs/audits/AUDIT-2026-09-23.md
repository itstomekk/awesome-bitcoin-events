# Repository audit — 2026-09-23

**Goal this audit is measured against:** a classic *awesome list*, where `README.md` is the
single, hand-edited source of truth and everything else (website, archive, map) is
optional and derived from it.

**This PR changes no behaviour and no data.** It adds this report and explanatory
comments in the code (look for `AUDIT NOTE`). Event files, `README.md`, `EVENTS.md`,
`data/` and `sources/` are untouched. The built site has the same content as `main`
(only the order of map points differs, which already varies between builds).

---

## 1. How the repo works today

```
            research (sources/raw/*.json, research/*.json)
                          │  scripts/import_source_scan.py  (historical)
                          ▼
 root events.json ──► data/events.json ──► src/content/events/<year>/*.md   ◄── CANONICAL TODAY
 (legacy v1)   migrate_legacy   migrate_events_to_markdown      (109 files)
                                                                    │
                     ┌──────────────────────────────────────────────┼──────────────────────┐
                     ▼                                              ▼                      ▼
   scripts/build_event_lists.mjs                         Astro build (src/)         CI check
   └─► README.md (upcoming table, GENERATED)             └─► GitHub Pages site      (fails if README
   └─► EVENTS.md (full archive, GENERATED)                   + 109 detail pages      table edited by hand)
```

* **Canonical data:** 109 Markdown files, each with ~80 lines of YAML (`maintainer:` block
  with verification, sources, coordinates, legacy payload). The prose body is empty in every file.
* **README.md:** the "Upcoming events" table is **overwritten by a script**. CI
  (`npm run check:event-lists`) **fails any PR that edits it by hand.**
* **Website:** Astro static site, map (Leaflet/OpenStreetMap), filters, one page per event.

## 2. Gap vs. the README-canonical goal

| # | Finding | Why it matters for the goal |
| --- | --- | --- |
| G1 | README is generated from the event files; the dependency points the wrong way | This is the main change needed. Right now a contributor who edits README.md gets a failed CI run |
| G2 | **Three docs name three different sources of truth:** `PLAN.md` + `HANDOFF.md` → `data/events.json`; `CONTRIBUTING.md` → `src/content/events/*.md`; your intent → `README.md` | Contributors and agents will edit the wrong thing |
| G3 | Contributing takes 5 commands (npm install, generate, check, build, pytest) | An awesome list is contributed to by editing one file in the GitHub web UI |
| G4 | No `LICENSE` file (package.json says MIT) | awesome lists require one; CC0-1.0 is the convention for list content |
| G5 | Not in awesome format: no awesome badge, no table of contents, no `- [Name](url) - description.` items, no awesome-lint | Needed to be listed in sindresorhus/awesome |
| G6 | 19 of 43 upcoming events have **no official link** (aggregator-only), 61 records are unverified legacy imports | An awesome list entry is essentially *a link*; link-less rows don't fit the format |
| G7 | Per-event evidence (verification, sources, coordinates) has no place in a README | Must be decided: drop it, or keep it in a side file keyed by event |

## 4. Migration options to a README-canonical list

| | A. Pure awesome list (recommended) | B. README canonical + website derived from it | C. Keep current (files canonical) |
| --- | --- | --- | --- |
| Source of truth | `README.md` | `README.md` | 109 `.md` files |
| Contributing | edit one line in GitHub UI | edit one line in GitHub UI | issue form or 5-command workflow |
| Website/map | none (or GitHub renders README) | small script parses README → JSON → site | as today |
| Evidence/verification data | dropped (git history keeps it) or `data/evidence.json` | side file keyed by event slug | kept inline |
| Effort | ~½ day | ~1–2 days | 0 |
| Risk | lose map/filters | parser must tolerate hand edits | fails your stated goal |

**Suggested README shape (option A/B):**

```markdown
# Awesome Bitcoin Events [![Awesome](https://awesome.re/badge.svg)](https://awesome.re)

> Bitcoin conferences, meetups and festivals worldwide. Verified against organisers' pages.

## Contents
- [2026](#2026) · [2027](#2027) · [Recurring meetups](#recurring-meetups) · [Past events](#past-events)

## 2026

### October
- [TABConf 8](https://tabconf.com/) - Atlanta, USA · Oct 12–15 · Technical conference.
- [Plan ₿ Forum Lugano](https://planb.lugano.ch/planb-forum/) - Lugano, Switzerland · Oct 23–24.
```

Rules that make the README parseable later (option B) and lintable now:
one event per line, `- [Name](official-url) - City, Country · Mon D–D · note.`;
events without an official URL stay out of the README (keep them in an issue or a
"to verify" file); past events move to `PAST.md` (or a `<details>` block) yearly.

**CI for an awesome list:** `awesome-lint` + a link checker (lychee) on PRs, and optionally a
weekly scheduled link check that opens an issue for dead links.
